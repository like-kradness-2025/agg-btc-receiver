# WS 復旧経路の修正案 v2（Astra P1 ①②③ への対応）

対象: `lib/base-connector.mjs`, `lib/binance-connector.mjs`
前提（実測 2026-09-23/24）:
- pong 途絶検知（15秒）は実地で有効（23:30 の Binance 事象で欠落 30〜38秒 → 17〜18.5秒）。
- ただし 23:30 の再接続後に `init sync failed after 3 retries`（binance_perp は 10 retries）が連発し、
  binance_perp が 23:33:26〜23:38:28 の約5分間データを出さなかった（23:33:14 に別作業で再起動が重なった）。
- 誤判定2種（未応答回数での66回誤爆／旧接続の lastPong 適用の4回誤爆）は修正済み。

v1 への Astra 再監査（P1×4）を反映した版。v1 の不足は「タイマー解放」「同期 Promise の await 後」
「WS 生存＝購読成立ではない」「バッファ維持の環状上書き」の4点だった。

## A. 世代境界（前回 P1③ / v1 監査 P1①②）

1. `pong` ハンドラ: 世代不一致なら **liveness を更新しない**（旧ソケットの遅延 pong を新接続の証拠にしない）。
2. タイマーは**ソケット所有**にする: open 時に `{ generation, pingTimer, appHeartbeatTimer }` を1組だけ保持。
   - `close` は**自分の世代のタイマーだけ**止める（世代不一致の close は何もしない）。
   - `disconnect()` / `_handleSequenceGap()` / `_reconnectNow()` は**世代を進める前に**明示的にタイマーを解放する。
   - `_clearTimers()` を ping / アプリ heartbeat も解放するよう拡張（現状は解放しない）。
   - 検証: 世代を進める経路すべてで、ping / heartbeat タイマーが残らないことをテストで固定。
3. 同期 Promise に世代を持たせ、**`await` の後と `catch` の両方**で失効判定する:
   `gen !== this._wsGeneration || this._isShuttingDown || this._state === 'disconnected'` なら破棄（再接続を予約しない）。
4. **自然 close も世代を進める**（close ハンドラで現在世代のソケットが閉じたら `_wsGeneration++`）。
   ＝ 飛んでいる同期は次の `connect()` を待たずに失効する。
5. 検証テスト: 旧世代の pong / close / 同期完了（resolve と reject の両方）が、新接続の liveness・
   タイマー・再接続予約・状態を変えないこと。

## B. 同期失敗の扱い（前回 P1① / v1 監査 P1③④）

**原則: WS を捨てるのは「WS 自体が死んだ」か「購読が成立していない」か「バッファが溢れた」場合だけ。**

1. 状態を明示する: `syncing-rest`（REST snapshot 待ち）／`retrying-rest`（待機つき再試行）。
   同期失敗しても `error` に落とさない（`error` にすると close の再接続と stale 監視の対象から外れるため）。
2. WS 生存中は**購読を維持**し、`retrying-rest` で REST 同期のみ再試行（待機は 1s→2s→4s…上限30s、上限回数あり）。
   受信中フレームは**適用せずリングバッファに保持**する。
3. **WS を捨てて作り直す**条件（いずれか）:
   - ソケットが閉じた/エラー、
   - **購読が成立していない**（`subscribe-tracker` で未 ack または失敗）＝ WS 生存と購読成立は別、
   - リングバッファ（65,536）が**溢れた**。
4. **バッファは snapshot 成功時にのみ、到着順に適用**する。`_syncBook()` 再呼び出しが先頭でバッファを消す挙動は
   「保持してから成功時に適用」へ変える。同期失敗で破棄する場合は**ログを1行**残し、未同期の板に適用しない。
   ＝ 溢れた/順序が保証できないバッファを「同期成功」として扱わない。
5. 重複購読の防止: 再試行では**購読を送り直さない**（送るのは WS を作り直した場合のみ）。購読の状態は
   `subscribe-tracker` を唯一の判断材料にする。
6. 検証テスト: WS 生存中の同期失敗で WS が再作成されない／購読維持される／バッファが到着順で適用される／
   溢れたら再接続に落ちる／購読未成立なら WS を作り直す。

## C. バックオフ（前回 P1② / v1 監査 P1②）

1. 試行回数は **open で 0 に戻さない**。**安定稼働（例: 同期成功後60秒無事）を確認して初めて 0 に戻す**。
2. 連続失敗は**上限つき指数バックオフ＋jitter**（1s→2s→4s…上限30s）。上限で頭打ちをテストで固定。
3. 検証テスト: 連続失敗で待ち時間が単調増加し上限で止まる／60秒の安定後にリセットされる。

## やってはいけないこと
- リトライ回数を増やすだけの対処（原因は「WS ごと捨てる」こと）。
- データ無音閾値（30秒）や pong 閾値（15秒）の変更。
- バッファ/フラッシュの分割（順序保証が崩れる）。
- **購読未成立のまま WS を維持する**こと／溢れたバッファや順序不明のバッファを適用すること。
- 同期失敗を `error` 状態にして監視・再接続の対象外にすること。

## 実測してから決めること
- `init sync failed` の実体（REST snapshot か WS 購読 ack か）を失敗ログから分類する。
  分類できない場合は B の「WS を捨てない境界」と C のみ実装し、待機時間の調整はしない。

## 検証手順（着手後）
1. 変更した経路を実行するテスト。`npm test` が fail 0。
2. 反映: 本番ツリーで `git diff <commit> -- <file>` が空、`status --porcelain` が空。
3. 起動確認: `is-active`=active、`NRestarts` が増えていない、readiness（絶対パス・`ts_ms` が起動後かつ120秒以内）。
4. 反映後15分: `pong starvation` と `WS CLOSE` の件数（誤発火・再接続ループの再発確認）。
5. 次の実途絶で欠落秒数（17〜18秒の維持）と `init sync failed` の有無。

## D. v2 監査（P1×3）の反映

1. **新しい状態も監視対象に入れる**: `_startStaleTimer()` の対象状態は `running / connected / syncing` のみ。
   `syncing-rest` / `retrying-rest` を**追加**する（pong は返るのに配信が止まる停止を検出できるようにする）。
   - 明記: **30秒データ無音による再接続（stale）は B の「WS を作り直す条件」とは別物**で、
     新状態でも**そのまま有効**（無音30秒 → 再接続）。pong 途絶検知も状態に依存せず動き続ける。
   - ＝ 新状態は「REST 同期だけを粘る」ための状態であり、データ無音・pong 途絶の検知は止めない。
2. **バッファ適用中の失効を止める**: `_applyRingBuf()` → `_applyDiff()` → `_handleSequenceGap()` の途中で
   世代が進んでも現状はループが続き、`_syncBook()` が最後に `running` へ戻す。
   - 適用ループは**1件ごとに世代を確認し、失効したら即中断**する（残りは破棄）。
   - **成功を確定する直前にも世代を確認**し、失効時は `running` にしない（成功扱いにしない）。
3. **再試行上限に到達した後の復旧先を定義する**（v2 の空白）:
   - 上限到達時は `_startReconnect()` の catch へ投げない（生存・購読成立中でも WS を作り直してしまい B に違反）。
   - 代わりに **WS を作り直す第4の条件**として「**同期の再試行上限に到達し、かつバックオフが上限に達した**（＝持続的な失敗）」を追加する。
     C の上限つきバックオフがあるため、作り直しの連打にはならない。
   - 到達までは WS と購読を維持して再試行を続ける（バッファ溢れは条件3で先に再接続に落ちる）。
4. 検証テスト（追加分）: 新状態で stale 監視が働く／適用途中の失効で即中断し `running` にならない／
   上限到達後にバックオフ付きで1回だけ作り直す。

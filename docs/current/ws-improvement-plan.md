# 配信WS 改善案 v2（Astra監査の指摘を反映）

v1 は Astra の監査で **CHANGES-REQUIRED**。指摘は実装で裏が取れた（下の「確認結果」）。
優先順位を「欠落を直接減らす/回復する」順に組み直した。

## 0. 証拠の数え方（v1の欠陥を訂正）
24hの数字は**別々の集計**であり、単純に足せない:
- ログの `WS CLOSE` 136件（うち code=1006 が129件、1000が7件）＝ソケットが閉じた回数
- ログの `no message for` 44件＝**こちらの無音検知**で切った回数
- 監視(5分間隔)の `reconnecting` 記録 56件＝**5分サンプルで捉えた数**（取りこぼす/重複する）
→ 優先度判断に使う前に、**market×時刻で突合して重複を消す**（24h窓、秒精度）。v1の「56回」は監視の観測数。

## 確認結果（v1の前提の訂正）
- `_lastMsgAt` は **任意のメッセージ受信で更新**される（`base-connector.mjs:151,164,365`）→ heartbeat や
  一部チャンネルだけ生きている障害では**無音検知が働かない**（Astra指摘は正しい）。
- Bitfinex は `TradeOnlyConnector` を継承し、**板はWS snapshot で受ける**
  （`_bookChanId`/`_bookSnapshotReceived`, 63-167行）→ v1の「REST snapshotで回復済み」は誤り。
- Bybit は `op === 'pong'` のみ処理し、**購読ackの成否を見ていない**。
- Bitstamp は microtimestamp の順序検査あり。**`event_id`/`pre_event_id` の回復経路は未使用**。
- OKX は `event === 'error'` は処理するが、**60秒前の切替予告は未使用**。

## 改善案（v2・この順で実施）

### 1. チャンネル単位の配信監視（最優先・欠落に直結）
- 問題: いまの無音判定は「任意メッセージ」基準。heartbeat で更新されると **trades/板の停止を検知できない**。
- 案: **チャンネル別の最終データ時刻**（trades / depth）を持ち、venue別の配信上限を超えたら
  **そのチャンネルだけ再購読＋必要なら再同期**する（接続全体を切る前に、まず購読を張り直す）。
- 検証: 「heartbeatは来ているがチャンネルが停止」した回数と、再購読で復帰した回数を実測。
  接続の切断回数を増やさずに欠落を減らせるかを見る。

### 2. 購読の成立確認と再試行（欠落の隠れ原因）
- 問題: 接続は成立しても**購読が失敗/未成立**だと、そのチャンネルだけ永久に欠ける（Bybitのack未検証、
  Bitfinexは `error` を無視）。
- 案: 購読ごとに **ack確認・期限・再試行**を入れる（ackが来なければ一定時間で再送、N回失敗で再接続）。
- 検証: 「接続は up だが配信が無い」状態の発生数を実測（いまは検知できない）。

### 3. Bitfinex の info をコード別に扱う（v1の誤りを修正）
- 訂正: `please reconnect` は**切断の事前予告**であって、猶予時間や切替時刻の選択を保証しない。
  「infoなら再接続」は不可。
- 案: info を**コード別に分類**（通常info / 再起動 / 保守開始・終了）し、それぞれ
  「維持 / 再接続 / 再購読」を決める。`_bookChanId`・`_bookSnapshotReceived` の**再接続時リセット**、
  購読成功、新snapshot到着までの差分抑止をセットで確認する。
- 検証: 該当infoの出現回数、再接続時の板の再同期成功/失敗、trades重複の有無。

### 4. 文書化された回復経路の評価（実装前に効果を見積もる）
- Bitstamp: `event_id`/`pre_event_id` による欠落検知・回復 → 形式と回復範囲を確認
- OKX: 60秒前の切替予告 → **予告で能動的に張り直す**（切替に合わせる）
- Bitfinex: 再購読＋snapshot（既存）→ **回復範囲と重複排除**を検証
- 注意: **板の現在状態の復元 ≠ 失った raw 差分の復元**（深度は回復してもdiffは戻らない）。

### 5. 閾値設計（実測が前提・v1の数値を撤回）
- v1の「OKXは20〜25秒で切る」は**撤回**（正常な待機を障害扱いし、接続・購読の空白を増やす）。
- 分離して設計する: ①生存確認を**開始**する時刻（例 20〜25秒）②応答期限 ③**データ停滞の判定**。
  ③の暫定候補は **35〜40秒**（サーバー仕様30秒＋配送/監視の余裕）＝**保証値ではない**。
  現在の5秒周期監視による検知遅延も織り込む。
- 検証: venue別に「再接続回数」「切断→復帰の秒数」「欠落秒数」。悪化したら戻す。

### 6. 接続寿命の管理（測ってから）
- 記録は実装済み（`pings`、close時のコード）。**`connectedAt` からの実経過時間**で評価する。
- 注意: 先回り切断は**欠落の時刻を移すだけ**になり得る（base は旧socketを閉じてから新接続）。
  「新を張ってから旧を閉じる（make-before-break）」が可能かを先に検討する。
  **Spot仕様をFuturesへ転用しない**（未確認のため）。

### 7. Bybit のアプリ層ハートビート（優先度を上げる）
- 仕様準拠の `{"op":"ping"}` を送る（間隔の根拠は仕様で確認する。v1の20秒は根拠なし）。
- タイマーの後始末と**応答監視**をセットにし、**pongがデータ停滞を隠さない**設計にする（案1と整合）。
- 対象は spot/perp の両方（v1はperpのみ想定していた）。

## やらないこと
- 閾値の一律短縮／無音閾値の延長(30→60秒)／根拠のない buffer・flush 分割
- **20〜25秒での強制切断**（v1案の撤回。正常待機の誤検知を招く）

## 進め方
1. 証拠の突合（§0の重複除去）と、案1・案2の実測準備（いま検知できていない状態の可視化）
2. 案1 → 案2 の順で実装（どちらも「接続を切らずに欠落を減らす」方向）
3. 案3・案4 は実測結果を見て採否
4. 実装が固まったら **Astra の最終監査**（1回）→ 本番反映

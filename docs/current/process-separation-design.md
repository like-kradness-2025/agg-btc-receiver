|---|---|---|---|

除外できた原因（実測）: **回線全体**（ICMP 9時間40分健全・異常0件）／**GC**（124件・最大8ms）／**計測済み処理**（`writeBatch`・IPC送出は spans=none）／**遅着処理**（停滞前後30秒にログ0行）。

## 2. 現状の責務マップ（実測）

Receiver（`agg-btc-receiver`）の中で3役割が同居している:

1. **受信**: WS購読・venue差の吸収・接続制御（keep-alive／保守通知／再購読）— `lib/orderflow-worker.mjs` の `connectMarket()`
2. **整理**: watermark・遅着ルート・backfill 振り分け — `lib/raw-sqlite-writer.mjs` / `raw-rotation-writer.mjs`
3. **板更新**: 板の維持・同期境界の証明（fail-closed） — `_syncBook()` 経路

Downstream（`agg-btc-downstream-live`）は**別系統の後工程**（本設計の対象外 ✓）

## 3. 目標構造（**3プロセス ＋ 共通の起動・監視・停止管理**）

| プロセス | 責務 | 境界（現物） |
|---|---|---|
| **受信** | WS購読・venue差の吸収・接続制御 | `connectMarket()` の `connect()` |
| **整理** | **watermark・遅着・backfill 判定を単独所有** | `prepareMarket()` のイベント配線／`queueRawWrite()` |
| **板更新** | 板の維持・同期境界の証明（fail-closed） | `connectMarket()` の `_syncBook()` |

- 受信 → 整理: `buildRawDbEnvelope()` 相当のイベント ＋ **受信時刻・接続ID・連番**（＋別系統の `canonicalFrame`）
- 整理 → 受信: **耐久化済み範囲の非同期 ACK** ＋ 失敗／容量状態
- 板更新へ: **受信順の入力**（並び替えは板の責務ではない）
- **共通管理**: 3プロセスの起動・監視・停止（単一の構造として見る ✓）
- ※ connector 内部の切断位置は**未確認**（Step 1 で確定）

## 4. 不変条件（重要順）

1. **接続世代と購読単位の順序**を守る／同期中 diff は**欠落なし・二重適用なし**／**旧世代の同期結果は拒否**／**境界証明まで `running` にしない（fail-closed）**
2. **受信メタデータは不変**／**耐久化完了前に ACK・再開位置を進めない**／再送は**冪等**／有界キュー満杯でも**黙って捨てない**（保持不能なら**欠測を明示して停止**）
3. **raw は完全・追記のみ**（過去の重複行を消さない）
4. **同じ処理を2箇所に持たない**（移すなら旧経路を消す）
5. **各プロセスは自段の障害だけを落とす**（板更新が死んでも受信は止まらない）
6. **優先順位**: **raw の完全性 ＞ 受信の継続 ＞ 監視記録**（記録できないなら停止して可視化）

## 5. 引継ぎ契約（所有者を固定）

### 5.1 既存で保証済み（`data-contract.md`）
- `recv_ts_ms` は socket 境界で確定し **replay 後も不変**／`recv_mono_ns` は**同一接続内で厳密単調増加**
- **append-safe 重複排除**: `(connection_id, receive_seq)` が既存なら **skip**（UPDATE しない）
- **板同期境界は source time で証明**、不能なら **fail-closed**
- 再試行中に buffer された diff は**失われず・二重適用もされない**

### 5.2 所有者（本設計で固定）
| 項目 | 所有者 |
|---|---|
| watermark・遅着・backfill 判定 | **整理**（単独所有） |
| 処理済み境界＝**再開 cursor** | **整理**（Downstream ではない ✗） |
| 同期境界の証明・世代判定 | **板更新** |
| 耐久化 ACK | **整理**（受信は待たない） |
| venue差（keep-alive・保守通知・購読） | **受信** |

### 5.3 stage 境界（原子性）
- **派生は冪等**（`(market, connection_id, receive_seq)` 単位）＋**watermark と派生の確定を単一 tx**
- DB を跨ぐ場合は **`pending_boundary` の印**を watermark 前進と同一 tx で書き（fsync ✓）、派生適用後に消す ✓／**起動時に印を解決**してから新規データを消費 ✓／解決失敗は **fail-closed** ✓

## 6. 障害時の振る舞い

1. 一時的な詰まり → **有界キュー**
2. 溢れ → **ディスク spool**（追記のみ・順序維持）
3. **spool 上限**（既定 空きの5%か2GB の小さい方）／**spool 書き込み失敗**（ENOSPC・IOエラー）→ **受信を停止**し `data_complete=false` ＋ **欠測区間を記録**
4. **記録先にも書けない** → **非ゼロ exit**（黙って欠落を続けない）

## 15. Astra 最終監査（2回目）の反映 — 二段印の定義

- 印は **watermark 側DBに1行**（`pending_boundary`）／**watermark 前進と同一 tx で書き fsync** ✓
- 順序: **印 → 派生を冪等適用 → 印を消す**（派生 commit 後 ✓）／同一 DB は単一 tx で印不要 ✓
- 再開: **新規データ消費前に印を解決**（境界までの派生を再適用 → 印を消す ✓）／失敗は **fail-closed** ✓
- 検証: 「印を書いた直後に kill → 再開」で派生が raw と一致・二重適用なし ✓

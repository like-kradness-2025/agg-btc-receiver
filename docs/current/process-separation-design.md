## 1. なぜやるか（実測）

直近24時間の実停滞は **worker 単独が2件のみ**:

| 時刻 | label | max_lag | spans |
|---|---|---|---|
| 11:08:03 | worker:E (kraken_spot) | 7,961ms | none |
| 15:46:08 | worker:C (coinbase_spot) | 21,249ms | none |

除外できた原因（すべて実測）: **回線全体**（ICMPは9時間40分健全・異常0件）／**GC**（124件観測・最大8ms）／**計測済み処理**（`writeBatch`・IPC送出は spans=none＝動いていない）／**遅着処理**（停滞前後30秒にログ0行）。
→ 残るのは **受信〜板更新が同じスレッドで同居している経路**（ここだけ span が無い）。

## 2. 現状の責務マップ（実測）

- `lib/orderflow-worker.mjs`（市場ごと1 worker）: **WS受信＋板の維持＋raw/canonical 送出**
- `raw-sqlite-writer.mjs` / `raw-rotation-writer.mjs`: **watermark・遅着ルート判定・backfill 振り分け**
- Tier は既に分離: **Receiver**（market別 SQLite のみ生成）→ **Downstream**（stage別 SQLite / 板再構築・特徴量）

## 3. 目標構造（**2プロセス**・確定）

1. **Receiver**（`agg-btc-receiver`）: WS受信 → **raw 追記** ＋ **隔離された板同期境界の証明**
2. **Downstream**（`agg-btc-downstream-live`・既存）: **整理・watermark・遅着・板の再構築**

- **organizer を独立プロセスにしない** ✓（段を増やさない／整理は既に Downstream と writer 層にある）

## 4. 不変条件

- **受信は下流の応答を待たない**（同期呼び出し・無界キュー・ブロッキング書き込みの禁止）
- **キューは有界**。溢れは必ず記録（黙って落とさない）
- **raw は完全・追記のみ**（過去の重複行を消さない現行方針を維持）
- **同じ処理を2箇所に持たない**（移すなら旧経路は消す）
- **各段は自段の障害だけを落とす**（Downstream が死んでも Receiver は継続）
- **優先順位（sol P1-2）**: 「raw の完全性」＞「受信の継続」。両立できない場合は **raw を守り、欠測区間を明示して受信を止める**（黙って欠落させない）

## 5. 引継ぎ契約（責任の確定）

### 5.1 既存で保証済み（`data-contract.md`）
- `recv_ts_ms` は socket 境界で確定し **replay 後も不変**
- `recv_mono_ns` は**同一接続内で厳密単調増加**
- **append-safe 重複排除**: `(connection_id, receive_seq)` が既存なら **skip**（UPDATE しない）
- **板同期境界は source time（microtimestamp）で証明**、不能なら **fail-closed**（`running` に遷移しない）
- 再試行中に buffer された diff は**失われず・二重適用もされない**

### 5.2 v2 で新たに確定（sol P1-1）
- **永続化 ack の確定者**: raw 追記の耐久完了（＝SQLite の commit 完了）を **Receiver の writer 層だけが ack** する。受信ループは ack を待たない（非同期で受ける）
- **再開 cursor の確定者**: **Downstream** が「処理済み境界」を確定する。確定の表現は **イベント単位**（market・connection_id・receive_seq の範囲）とし、**バイト位置だけに依存しない**（`incremental-cursor` は補助情報に格下げ）
- **順序**: ①受信 → ②raw 永続化（ack）→ ③Downstream 処理 → ④境界確定。**④より前のイベントは再開時に再処理され、重複排除で吸収される**（＝少なくとも二重処理に倒す。取りこぼしに倒さない）

### 5.3 stage 境界（唯一の残課題）
- watermark と派生の**原子 commit** の表現方法（§9-1）

## 6. 障害時の振る舞い（sol P1-2 の答え）

段階的な退避で「受信を止めない」を最大化し、**最後は raw を守る**:

1. 一時的な詰まり → **有界キュー**（メモリ）で吸収
2. キュー溢れ → **ディスク spool へ退避**（追記のみ・順序維持）
3. **spool 上限到達**（既定: 空き容量の5%または2GBの小さい方／設定可能）→ **受信を一時停止**し、`data_complete=false` ＋ **欠測区間を明示記録**（fail-loud）
4. 復旧後は spool から順に流し、**停止区間を「欠測」として下流に伝える**（遡って欠落を埋めたように見せない）

## 7. 段階移行（2プロセス方針に統一）

- **Step 0（進行中）**: 計測で**隔離対象を特定**（停滞時の全worker遅れ履歴＋受信〜板更新の span）
- **Step 1**: **境界証明の隔離**（受信I/Oループから板同期境界の証明を外す）
- **Step 2**: 整理の責務を Downstream／writer 層へ完全集約（Receiver から watermark 参照を外す）
- **Step 3**: raw 追記の耐久性強化（spool と ack の実装・検証）

各 Step: 事前に期待値とロールバック手順を提示 → 実施 → 実測比較 → 問題があれば**環境変数1つで旧経路へ戻せる**状態を保つ。

### 7.1 Step 1 の引継ぎ条件（sol P1-3）
隔離しても次を**現行どおり保つ**（実装済みの世代境界と同じ保証）:
- **接続ごとの diff 順序**（`chanId`／購読単位の厳密振り分けを含む）
- **再接続時の世代切替**（旧世代の pong・フレーム・同期結果を新世代に混ぜない）
- **証明失敗時の fail-closed**（`running` へ遷移しない）
- 同期中に buffer されたフレームの**欠落なし・二重適用なし**

## 8. 受け入れ条件（一本化）

## 14. Astra 最終監査（1回目）の反映 = v3

### 14.1 派生側の原子性（P1・§5.2-5.3 / §9-1）
- **問題**: 再開時の再処理は、raw の重複排除だけでは**派生の二重適用**を防げない ✗
- **決定（2段構え）**:
  1. **派生は冪等にする** — 同一 `(market, connection_id, receive_seq)` に対する派生更新は**何度適用しても同じ結果** ✓
  2. **watermark と派生の確定を1トランザクションで commit**（同一 DB 内は1 tx ✓）。跨ぐ場合は「**確定前に印を付け、確定後に印を消す**」＋冪等で吸収 ✓
- **検証**: 「処理の途中でクラッシュ → 再開」のテストで、**派生の件数と値が raw と一致**することを確認 ✓
- → **§9-1（stage 境界）はこれで解消** ✓：stage 境界 = **「冪等な派生 ＋ 単一 tx（または二段印）」**として定義

### 14.2 spool 失敗時の停止条件（P1・§6）
- **追加**: spool への**書き込み自体が失敗**（ENOSPC／I/O エラー）したら、**上限未到達でも受信を停止**し、欠測区間を記録 ✓
- **最後の砦**: **記録先にも書けない場合**は **プロセスを異常終了**（非ゼロ exit ✓）
  ＝「黙って欠落を続けるより落ちて可視化する」✓（systemd の再起動＋監視で気づける ✓）
- **優先順位（確定）**: **raw の完全性 ＞ 受信の継続 ＞ 監視記録**（記録できないなら停止して可視化 ✓）

### 14.3 Step 1 の扱い（Astra 判断）
- **Step 1（境界証明の隔離）は着可** ✓
- 条件: **既存の永続化・cursor 経路を変更しない**範囲で、**§7.1 の4条件を満たす隔離**に限定 ✓
- **14.1・14.2 は「該当経路を変更する前」に解消**すること ✓（該当経路＝raw 永続化と cursor 確定／spool 導入 ✓）

## 15. Astra 最終監査（2回目）の反映 — DB 跨ぎ「二段印」の定義

指摘: 二段印は**印の永続化・commit 順序・再開時の回復手順**が未定義 ✗／**watermark だけ確定して派生が未反映**の状態は**冪等性だけでは防げない** ✗

### 15.1 印の永続化
- 印は **watermark 側の DB に1行**（`pending_boundary`: `market` / `stream` / `boundary_seq` / `boundary_ts_ms` / `created_at_ms`）
- **watermark を進めるのと同じトランザクション**で書き、**fsync 完了後**に次の段へ進む ✓
  ＝「印が残っていないのに watermark だけ進む」状態を作らない ✓

### 15.2 commit 順序（跨ぐ場合）
1. **印を書く**（watermark 前進と同一 tx ✓／fsync ✓）
2. **派生を冪等に適用**（`(market, connection_id, receive_seq)` 単位 ✓）
3. **印を消す**（派生の commit 完了後 ✓）

同一 DB に収まる場合は**単一 tx で足りる**（印は不要 ✓）

### 15.3 再開時の回復手順
- **起動時、新規データを消費する前に**印を解決する ✓
  - 印がある → **その境界までの派生を再適用**（冪等 ✓）→ 印を消す ✓
  - 再適用に失敗 → **fail-closed**（watermark を進めない ✓／受信は raw 追記のみ継続 ✓／未確定として記録 ✓）
- **検証テスト**: 「印を書いた直後に kill → 再開」で、**派生が raw と一致**し**二重適用が無い**ことを確認 ✓

### 15.4 これで閉じる範囲
- §9-1（stage 境界）は「**冪等な派生 ＋ 単一 tx（跨ぐ場合は §15.1〜15.3 の印）**」として**定義完了** ✓

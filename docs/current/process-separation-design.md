# 受信・整理・板更新のプロセス分離 設計書 (v1・未承認)

- 状態: **設計段階 / コード変更なし / Astra・luna レビュー前**
- 目的: worker 単独の数秒〜20秒級の停滞を**構造的に起こりにくくする**（故障隔離）
- 入力として先に読むべき既存文書: `docs/current/data-contract.md` / `canonical-pipeline.md` / `fix-map.md` / `operations.md`
- この文書は「境界・不変条件・引継ぎ契約・移行手順」だけを決める。実装の詳細は Step ごとの別紙にする。

## 1. なぜやるか（実測に基づく）

直近24時間の実停滞は **worker 単独が2件のみ**:

| 時刻 | label | max_lag | spans |
|---|---|---|---|
| 11:08:03 | worker:E (kraken_spot) | 7,961ms | none |
| 15:46:08 | worker:C (coinbase_spot) | 21,249ms | none |

除外できた原因（いずれも実測）:

- **回線全体の停止**: ルーター＋外部への ICMP は9時間40分健全・異常0件
- **GC**: PerformanceObserver で 124件観測、最大 8ms（通常はミリ秒）
- **計測済みの重い処理**: `writeBatch`・`ipc_send_raw`・`ipc_send_canonical` は span 計測済みで、停滞時に **spans=none**＝動いていなかった
- **遅着処理(backfill)**: 停滞の前後30秒にログ0行（24時間で226回動いているが、この2件の時刻には不在）

残るのは **受信〜板更新が同じスレッドで同居している経路**。ここだけ span が無く、止まっても他が気づけない。

## 2. 現状の責務マップ（実測）

- `lib/orderflow-worker.mjs`（市場ごと1 worker）: **WS受信＋板の維持＋watermark参照＋raw/canonicalの送出**
- `lib/raw-sqlite-writer.mjs` / `raw-rotation-writer.mjs`: **watermark・遅着ルート判定・backfill への振り分け**（＝整理の一部は既に受信の外にある）
- `lib/downstream/`（Node/Python）: **板の再構築・バースト検出・特徴量・commit**

→ つまり「整理」は既に一部分離済み。**同居が残っているのは受信と板更新**。

## 3. 目標構造

3プロセスを「1つの構造」として運用する（それぞれ独立に再起動でき、単一障害点を作らない）:

1. **receiver**: WS購読 → **raw 追記のみ**（＋seq/時刻のメタ情報）。下流を待たない。
2. **organizer**: 順序づけ・watermark・遅着イベントの扱い（現 writer の役割を昇格）。確定境界を出す。
3. **book**: 板の再構築・派生入力の生成（下流の板再構築を担う）。

## 4. 不変条件（ここを破る変更は不可）

- **受信は下流の応答を待たない**（同期呼び出し・無界キュー・ブロッキング書き込みの禁止）
- **キューは有界**。溢れたら**必ず記録**し、勝手に落とさない（欠測区間として下流に伝える）
- **raw は完全・追記のみ**（過去の重複行を消さない現行方針を維持）
- **同じ処理を2箇所に持たない**（移すなら旧経路は消す。二重実装は作らない）
- **各段は自段の障害だけを落とす**（book が死んでも receiver は止まらない）

## 5. 引継ぎ契約（Astra 監査の最重要点）

「どこまで処理済みか」を **バイト位置だけで表現しない**。必要な保証は次の3つを同時に:

1. **完全性**: 境界より前のイベントは漏れなく処理済み
2. **重複排除**: 再開時に同じイベントを二重に処理しない
3. **原子性**: raw の追記と派生物の確定が**同じ境界**で一致する（片方だけ進まない）

現状 `incremental-cursor` は**バイト位置のみ**を保存するため、上記の保証範囲を**実測で確認してから**設計に落とす（未確認のまま切替は不可）。

## 6. 障害時の振る舞い（分離が悪化させないための条件）

- 下流停止中: receiver は**記録を残して継続**（溢れは「欠測区間」として明示）
- 溢れ発生時: **raw を守る**ことを最優先（派生物は後から作り直せる）
- 再起動時: 各段が**自分の境界から再開**。境界の巻き戻しは許容（重複排除で吸収）
- 遅着イベント: **捨てない**（現行どおり backfill へ）

## 7. 段階移行（小出しにしない・各段でゲートを切る）

- **Step 0（進行中）**: 計測で**原因を名指し**する（停滞時の全worker遅れ履歴＋受信〜板更新の span）
- **Step 1**: 名指しされた**1処理だけ**を分離（最小変更。効果測定）
- **Step 2**: 「整理」を organizer として完全分離（writer の昇格）
- **Step 3**: 「板更新」を分離

各 Step: 事前に期待値とロールバック手順を提示 → 実施 → 実測比較 → 問題があれば**環境変数1つで旧経路へ戻せる**状態を保つ。

## 8. 受け入れ条件

- **停滞ゼロ**（24時間で worker 単独停止が0件）
- **欠落ゼロ・重複ゼロ**（raw と派生物の突合で件数一致）
- **遅延・スループットが現行以上**（板の更新遅延・記録レート）
- **監視が3プロセスを網羅**（生存・遅延・溢れの記録）

## 11. 既存契約との突合（2026-09-24 実測・§9 の答え合わせ）

設計を進める前に `docs/current/data-contract.md`（312行）と `canonical-pipeline.md` を読んだ。
**提案している「3プロセス構造」は既に Tier として存在している**:

- `canonical-pipeline.md` の **3-Tier 構成**: **Receiver**（`agg-btc-receiver.service`・market別 SQLite ✓）→ **Downstream**（`agg-btc-downstream-live.service`・stage別 SQLite `runtime/output-final/<stage>/<market>.sqlite` ✓）
- Receiver は **raw SQLite のみ**を生成し、Parquet/DuckDB/JSONL は作らない ✓

**引継ぎ契約は、少なくとも ingress と板同期境界については既に文書化・実装済み**:

| 保証 | 現行の実装根拠 |
|---|---|
| 受信時刻の固定 | `recv_ts_ms` は socket message 境界で確定し **buffer/replay 後も不変**、worker は再採番しない ✓ |
| 接続内の順序 | `recv_mono_ns`（monotonic・ナノ秒）が**同一コネクション内で厳密単調増加** ✓ |
| 重複排除 | **append-safe**: `(connection_id, receive_seq)` が既存なら **skip**（既存行を UPDATE しない ✓）。REST等 `receive_seq=NULL` は常に追記 ✓ |
| 板同期の境界 | **source time（microtimestamp）で証明**。証明できなければ **fail-closed**（`running` に遷移しない ✓ 3回失敗で `error` ✓） |
| 再試行の不変条件 | 再試行中に buffer された diff は**失われず・二重適用もされない** ✓ |
